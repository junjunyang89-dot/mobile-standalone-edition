# 性能基础质量测试 - 后端需配合的调整

前端已按「性能报告」新接口与「执行时长」配置完成改造，后端需保证以下能力，否则性能报告无数据或执行时长不生效。

---

## 一、性能报告接口（必须）

### 1. 接口约定

- **路径**：`GET /api/functional-test/tasks/:taskId/performance-report`
- **含义**：仅对「性能基础质量测试」任务有效，返回**最新一次执行**的 `result_data` 解析后的 JSON。
- **非性能任务或尚无执行结果时**：返回 **404**，前端会展示「暂无性能报告数据」。

### 2. 返回 JSON 结构（与前端约定一致）

前端会直接用于「整体评估 / 遍历统计 / 资源数据 / 操作详情」展示，字段建议如下（可多不可少，多出的字段前端会忽略）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `traversalDurationMinutes` | number | 遍历时长（分钟） |
| `totalOperations` | number | 总操作次数 |
| `launchCount` | number | 启动次数 |
| `clickCount` | number | 点击次数 |
| `swipeCount` | number | 滑动次数 |
| `conclusion` | string | 测试结论文案（整体评估用） |
| `resourceSummary` | object | `cpuApp` / `memoryPss` 各含 `peak`、`min`、`avg`（数值） |
| `issueSummary` | object | `responseDelayCount`、`completionDelayCount`、`totalIssueCount`、`byOperationType` |
| `resourceSamples` | array | `{ timestampMs, cpuPercent?, memoryPssKb? }`，用于画 CPU/内存曲线 |
| `operations` | array | `{ index, type, startTimeMs, endTimeMs, responseDelayMs?, cpuAvgDuringStep?, memoryPssKbDuringStep? }` |

### 3. `issueSummary.byOperationType` 与前端表格的对应关系

前端「整体评估」里有一张**按操作类型的问题统计表**，表头为：操作类型(次数)、响应时延、完成时延、卡顿、音视频、黑白块。

- 每行的「操作类型」固定为：**启动操作**、**滑动操作**、**点击操作**、**观看视频**。
- 前端会从 `byOperationType` 里按**键**取各类型的响应时延/完成时延数量。建议后端键与上述一致，或至少支持下列之一（前端会依次尝试）：
  - 启动：`"启动操作"` / `"启动"` / `"LAUNCH"`
  - 滑动：`"滑动操作"` / `"滑动"` / `"SWIPE"`
  - 点击：`"点击操作"` / `"点击"` / `"CLICK"`
- 每项结构建议：`{ responseDelayCount?: number, completionDelayCount?: number }`。卡顿/音视频/黑白块列前端已预留，目前填 0；若后端后续有数据，可再扩展字段（如 `stutterCount`、`avCount`、`bwCount`）并在文档中说明。

**示例**：

```json
"issueSummary": {
  "responseDelayCount": 7,
  "completionDelayCount": 29,
  "totalIssueCount": 45,
  "byOperationType": {
    "启动操作": { "responseDelayCount": 0, "completionDelayCount": 10 },
    "滑动操作": { "responseDelayCount": 2, "completionDelayCount": 0 },
    "点击操作": { "responseDelayCount": 5, "completionDelayCount": 19 }
  }
}
```

## 二、创建任务时传入执行时长（必须）

### 1. 接口约定

- **路径**：`POST /api/tasks/test`
- 创建性能任务时，前端会在请求体中传：
  - `taskType: "PERFORMANCE_BASELINE_TEST"`
  - `platform`、`deviceId`、`appId` 等
  - **`config`**：JSON 字符串，例如 `"{\"traversalMinutes\": 5}"`

### 2. 后端需要做的

- **解析并落库**：将 `config` 解析为对象，与现有 config（如 `appId`、`taskType`）合并后写入任务配置；不要丢弃 `traversalMinutes`。
- **执行时使用**：运行性能测试时，从该任务的 config 中读取 `traversalMinutes`，作为遍历时长（分钟）。建议限制在 **1～60**，未传或非法时用默认值（如 2）。

**请求体示例**：

```json
{
  "taskType": "PERFORMANCE_BASELINE_TEST",
  "platform": "ANDROID",
  "deviceId": "xxx",
  "appId": "yyy",
  "config": "{\"traversalMinutes\": 5}"
}
```

## 三、若后端是当前仓库的 Node 服务（server/index.ts）

当前本仓库的 Node 服务需要做两处改动，才能和前端对齐。

### 1. 创建任务时把 `config` 里的执行时长存进去

- **文件**：`server/index.ts`
- **位置**：`POST /api/tasks/test` 中构造 `config` 的地方。
- **现状**：只传了 `config: { appId, taskType }`，没有把请求体里的 `config` 字符串解析合并进去。
- **建议**：  
  - 读取 `body.config`（可能是 JSON 字符串，如 `"{\"traversalMinutes\": 5}"`）。  
  - 若存在且为字符串，则 `JSON.parse(body.config)`，与 `{ appId, taskType }` 合并（注意不要覆盖已有 appId/taskType）。  
  - 合并后的对象再传给 `taskManager.createTask` 的 `config`。  
  - 这样任务里会带上 `traversalMinutes`，实际执行性能测试的模块（若在本仓库或由本服务调用）可从任务 config 中读取并生效。

### 2. 新增「性能报告」接口

- **文件**：`server/index.ts`
- **路径**：`GET /api/functional-test/tasks/:taskId/performance-report`
- **逻辑建议**：  
  1. 根据 `taskId` 查任务；若不存在则 404。  
  2. 若任务的 `config.taskType !== 'PERFORMANCE_BASELINE_TEST'`，可返回 404（仅性能任务可查报告）。  
  3. 查该任务**最新一次执行**（如从 `task_executions` 表按 `task_id` + `start_time` 降序取一条）。  
  4. 若没有执行记录，或该执行没有 `result_data`，返回 404。  
  5. 若有 `result_data`（一般为 JSON 字符串），解析后直接作为响应 body 返回（前端期望的就是 PerformanceTestResultDto 结构）。

**注意**：当前 `task_executions` 表结构里**没有 `result_data` 字段**。若性能测试是由本 Node 服务或同仓库内的 runner 执行的，需要：

- 在 `task_executions` 上增加 `result_data TEXT`（或等价类型），并在执行完成时把性能测试结果 JSON 字符串写入；  
- 或由实际执行性能测试的进程/服务写入带 `result_data` 的库表，本接口只读该表并返回。

若性能测试实际由**其他后端（如 Java）**执行并写库，则 `GET /api/functional-test/tasks/:taskId/performance-report` 应在那个后端实现，并保证返回上述 JSON 结构；本 Node 服务可转发或不再提供该接口（由前端直连该后端即可）。

## 四、任务列表与概览（建议）

- **任务列表**：若按任务类型展示，请返回 `taskType: "PERFORMANCE_BASELINE_TEST"`，前端已做枚举到「性能基础质量测试」的映射。
- **任务概览**：`GET /api/functional-test/tasks/:taskId/overview` 对性能任务应照常返回，且 `summarySectionTitle` 建议为 **「性能测试结果」**，`testType` 建议包含 **「性能」**，前端会据此识别为性能任务并展示「性能报告」区块及拉取 performance-report。

---

## 五、小结

| 项 | 说明 |
|----|------|
| **性能报告接口** | 实现 `GET /api/functional-test/tasks/:taskId/performance-report`，仅性能任务、有最新执行且带 result_data 时返回解析后的 JSON，否则 404。 |
| **执行时长** | `POST /api/tasks/test` 解析并保存 `config.traversalMinutes`，执行时按 1～60 分钟限制使用。 |
| **byOperationType 键** | 与前端表格一致：启动操作/滑动操作/点击操作（或 启动/滑动/点击 或 LAUNCH/SWIPE/CLICK）。 |
| **Node 服务** | 若为本仓库 server：① 创建任务时合并 body.config；② 新增 performance-report 接口，且 task_executions 需能提供 result_data（表结构或由执行端写入）。 |

按上述调整后，前端的「性能报告」会从新接口拿到数据并正常展示，执行时长也会按用户选择生效。
